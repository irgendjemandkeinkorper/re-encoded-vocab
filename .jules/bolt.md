# BOLT'S JOURNAL - RE-ENCODED VOCABULARY OPTIMIZATIONS

## 2026-07-28 - [Levenshtein & checkAnswer Optimization]
**Learning:** In interactive single-page web applications with inline JS, performance bottlenecks often hide in algorithmic loops that execute on user interactions. The original `checkAnswer` recreated a complete multi-hundred entry word bank on every typed keystroke/submit and ran a full 2D grid allocation Levenshtein distance matching loop on all of them, causing excessive GC pressure and CPU cycles. Cache the word bank on quiz start instead of recreating it on submission. Optimize Levenshtein to use two 1D arrays for dynamic programming (O(N) space instead of O(N^2)). Use early length-difference pruning during the fuzzy matching loop to immediately skip Levenshtein computation if the absolute length difference of the candidate word and the input is greater than or equal to the best distance found so far. Prioritize computing the correct term's variants first to establish a tight distance baseline early, dramatically increasing pruning efficiency.
**Action:** Always cache lookup structures/word banks where possible across user sessions, use flat 1D space in matrix-based string algorithms in JS to avoid GC/allocation overhead, and employ early-exit/length-difference pruning to minimize expensive distance calculations.
