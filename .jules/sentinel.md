# Sentinel's Security Journal

## 2026-07-28 - [Stored XSS in Supabase Leaderboard Name rendering]
**Vulnerability:** The leaderboard page displayed player names retrieved from a Supabase database (`row.session_name`) using `.innerHTML` without any form of escaping or sanitization. This allowed any user to submit a name containing arbitrary HTML/JavaScript tags (e.g. `<img src=x onerror=alert(1)>`) and have it executed in other users' browsers when viewing the shared leaderboard.
**Learning:** Since the application is self-contained in a single `index.html` file and interacts directly with Supabase via CDN, security controls (like name length restrictions or alphanumeric validation) on the front-end inputs can be easily bypassed by interacting directly with the database or through DOM manipulation. Consequently, output sanitization is the ultimate line of defense for shared database data.
**Prevention:** Always use safe text insertion APIs like `.textContent` when possible, or run any dynamic content through an HTML entity escaping helper (like a robust `escHtml` function) before inserting it via `.innerHTML`.

## 2026-07-30 - [Input Sanitization and Content Security Policy Hardening]
**Vulnerability:** Although the leaderboard correctly used `escHtml` to escape HTML strings from the database before insertion, there was no input-level validation or sanitization on user-submitted names. Users could submit arbitrary HTML, script-injection payloads, or unvalidated strings to the Supabase backend. Additionally, the lack of a Content Security Policy meant that any successful XSS injection could load malicious external scripts or exfiltrate data without restrictions.
**Learning:** Defense-in-depth requires securing both input entry and output rendering, as well as restricting the execution environment itself. Restricting names to safe alphanumeric, dots, hyphens, and underscores prevents malicious inputs from ever entering the persistent store, while a strict meta CSP header prevents script injection and clickjacking at the browser execution level.
**Prevention:** Implement strict input sanitization helpers (like a regex-based `sanitizeName` function) for all user-submitted fields, and configure a strict Content-Security-Policy (CSP) meta tag in the HTML head to lock down permissible script, style, and connection origins.
## 2026-07-31 - [Defense-in-depth via file upload limits, input validation, and early slicing]
**Vulnerability:** Client-side file imports and text inputs lacked strict resource constraints. A user could upload a massive JSON file or a JSON array containing millions of items, which could cause client-side browser freezing, out-of-memory crashes, or Denial of Service (DoS). Additionally, unconstrained text inputs processed by regex-based cleaners (like `sanitizeName`) could trigger Regular Expression Denial of Service (ReDoS) or memory exhaustion if very long inputs were passed.
**Learning:** For a serverless, static single-page application with direct CDN dependencies, security constraints must be enforced on all input boundaries. Standardizing maximum file sizes (1MB), restricting parsed array lengths (1000 items), and slicing user inputs early (to 200 characters) before running regular expression matches ensures resource safety and robust defense-in-depth without requiring backend controls.
**Prevention:** Implement file size checks before reading files, enforce length limits on parsed JSON arrays, specify `maxlength` attributes on HTML text inputs, and always slice input strings early in sanitization functions before running potentially complex regex operations.

## 2026-08-01 - [Secure Clipboard Copy Utility and Fallback]
**Vulnerability:** The application invoked an undefined `copyToClipboard` function on clipboard actions, representing a functional gap and security risk if developers implemented insecure, custom inline alternatives (e.g. using unsafe DOM parsing or `innerHTML` elements for offscreen copying fallbacks).
**Learning:** Standard copy-to-clipboard patterns can fail in insecure contexts or restricted frames. Providing a single, centralized, secure utility prevents insecure ad-hoc solutions. Secure copying must utilize `navigator.clipboard` when available under `isSecureContext`, with a robust fallback to a temporary offscreen `<textarea>` using safe value assignment (`textarea.value = text`) rather than unsafe `innerHTML` to prevent DOM/XSS injection.
**Prevention:** Provide a standard utility for copy operations that enforces secure context verification and strictly uses safe text value assignments on temporary offscreen elements during sync fallbacks.

## 2026-08-02 - [Prototype Pollution and Prototype Collision in Leaderboard Frequency Accumulation]
**Vulnerability:** Accumulating username frequencies or counting occurrences using plain JavaScript objects (`{}`) can be exploited or crashed if a user registers/submits a username matching a built-in prototype property (e.g., `__proto__`, `toString`, `hasOwnProperty`).
**Learning:** For application features that accumulate, index, or group data by user-controlled keys, using a standard object `{}` introduces a risk where property resolution falls back to the prototype chain, causing logical errors, NaNs, or crashes.
**Prevention:** Always initialize accumulator or frequency-counter maps using `Object.create(null)` instead of `{}` to completely sever inheritance from `Object.prototype`.
