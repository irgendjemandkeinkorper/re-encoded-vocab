# v0.3 — Vocabulary Features

Improve the depth and completeness of the vocabulary/lens content itself, and keep
the fleet's own work non-redundant as PR volume grows.

## Tools
- Term/lens coverage check: `grep -c "cat:" index.html` for term count; inspect each
  `DATA[]` entry's `lenses{}` map for missing keys (should have all 7 of `sports`,
  `fandom`, `ttrpg`, `cooking`, `millennial`, `f1`, `gaming`).

## Assessment Hints
- Prioritize `DATA[]` entries that have no `lenses{}` map at all (pure medical-only
  fallback) over entries with partial lens coverage — the biggest single content gap
  is ~20 of 242 terms with zero non-medical lens translations.
- Do NOT touch `CODE_WALKS[]` / Code Lab structure for this milestone — that's UI/dev-tooling,
  not vocabulary content, and belongs to a separate goal.
- Small, targeted content PRs (a handful of terms per PR) are easier to review than one
  giant PR touching all 242 entries.

## Insight Hints
- Report which subjects/categories still have the most medical-only fallback terms.
- Note if any term's `analogy` field is empty or clearly a placeholder — that's a content
  gap even where a lenses{} map exists.

## Constraints
- Do NOT propose changes already covered by open issues.
- Do NOT propose changes rejected in recently closed issues.
- Before opening a PR, check open PRs for overlapping scope (e.g. another PR already
  touching the same `DATA[]` entries or the same performance hot path) — do not duplicate
  work that's already in flight or already merged. (This constraint exists because PR #21
  duplicated already-merged PR #24's debounce/DocumentFragment optimization.)
- Keep tasks small and isolated — one logical change per issue.
